# Lee Relay v4.1 — Blank-Slate Design

## Goal

Make Lee Relay feel like one simple product while adding the useful parts of a persistent multi-agent workspace:

`Room → Playbook → Run → Report`

The user should not have to understand the engine. A Room is a saved conversation, a Playbook is the purpose and procedure, a Run is one bounded execution, and a Report is the durable result.

## Invariants

- Existing provider adapters and background-tab control remain the delivery path. Gemini and Copilot must continue working when their tabs are not foreground tabs.
- Existing Interactive and Full Auto behavior remains available. Full Auto never accepts human composer text while it is live; pausing is the explicit way to join.
- A send action is at-most-once. Delivery and response verification remain separate transaction stages.
- One active Run is allowed at a time. Any number of saved Rooms can exist, but switching Rooms pauses/releases the current live run before loading the next Room.
- Live tab IDs, URLs, and transaction bindings never enter durable Room or Report data.
- Every autonomous route is bounded by a unified Run Budget: time, completed AI turns, and handoff hops. A disabled individual bound means unlimited for that bound, but the product still has provider/extension safety timeouts.
- Existing v3/v4 saved meeting data migrates without losing title, participants, transcript, mode, roles, session selection, or Loop Guard settings.

## Domain model

### Room

```text
Room {
  id, title, purpose, createdAt, updatedAt,
  meeting: durable meeting state,
  playbookId,
  runHistory: [{ id, status, startedAt, completedAt, artifact }]
}
```

Rooms are persisted in one versioned workspace document. The current active meeting runtime remains in session storage for crash recovery; the Room copy is the durable source of conversation history.

### Playbook

```text
Playbook {
  id, name, description,
  phases: [{ id, name, instruction, turnLimit }],
  output: { summary, phaseResults, scorecard, decisions, actionItems },
  builtIn | custom
}
```

Built-ins cover free discussion, 9-axis channel analysis, debate, planning review, and final summary. Existing `session.templateId` remains a compatibility alias for the built-in Playbook ID.

### Run

```text
Run {
  id, roomId, playbookId, status,
  startedAt, endedAt, phaseIndex,
  budget: { maxDurationMs, maxTurns, maxHops },
  turns, events, handoffs, stopReason,
  artifact
}
```

Run events are structured and bounded. An `@AI` route is recorded as a handoff event rather than hidden in a prompt string. Full Auto accepts a valid AI handoff automatically; Interactive uses an explicit handoff card/state and does not silently start a new AI turn from ambiguous text.

### Report / Artifact

The report is generated deterministically from the saved Run and transcript metadata. It contains a summary of the run, phase results, a 9-axis scorecard when the playbook provides axes, decisions, action items, and the complete transcript reference. Markdown, TXT, and JSON exports are local downloads and exclude live browser data.

## Routing

- `@Gemini`, `@Copilot`, `@ChatGPT`, `@Claude`, `@all`, and participant labels are recognized only when they are an intentional leading/directive mention, not when they appear in historical prose.
- A user directive selects the requested connected participant.
- In Full Auto, a clean AI response can propose the next participant with a directive mention. The engine records the proposed handoff, validates that the target is connected and distinct, then schedules it.
- Ambiguous, disconnected, malformed, or self-looping directives fall back to the safe round-robin route and create an activity event.

## UI

The primary side panel exposes only:

1. Room selector and “New room”.
2. Participant role chips.
3. Active Playbook summary and one compact “Change” action.
4. Transcript/composer.
5. One primary Run/Start button plus Pause/End.

Advanced controls are behind one disclosure area: Run Budget, retry/response timeout, screenshot policy, and diagnostic activity. Action-needed recovery remains visible only when required. Reports are accessed from the Room area, not mixed into the live transcript controls.

## Persistence and migration

- New storage key: `v4.1Workspace` in local storage.
- New session key: `v4.1ActiveRun` for the current runtime snapshot.
- First load wraps the existing v4.0.1 durable meeting in one Room named after its meeting title.
- Subsequent saves update both the active runtime and the active Room's durable meeting snapshot.
- Selecting a Room releases background-tab ownership, strips live bindings, loads the Room meeting into session storage, and broadcasts a complete state.
- Old keys remain readable for one-way migration; no destructive cleanup is performed automatically.

## Reliability boundaries

- The provider page remains the source of truth for delivery/response evidence.
- A service-worker watchdog remains independent of provider-page timers, preserving background-tab reliability.
- Room switching, Run start/stop, and export use the existing serialized event queue.
- No implementation claims mathematical “zero bugs”; acceptance is based on unit, contract, integration, package, and manual background-tab checks.

## Acceptance gates

- All existing tests continue to pass.
- New tests cover migration, multi-room persistence semantics, playbook snapshots, run budget decisions, `@AI` routing/handoffs, report exports, and public-state sanitization.
- `node --check` covers every new module and all extension scripts.
- Manifest/package verification passes for v4.1.0.
- A packaged ZIP contains only the declared extension capsule and can be verified by hash.
- Manual smoke test: Gemini and Copilot remain relayed while their tabs are backgrounded; switching Rooms preserves both transcripts; Interactive and Full Auto each complete a bounded Run.
